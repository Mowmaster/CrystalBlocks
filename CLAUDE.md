## Project state
- All blocks are "tintable": one non-ticking block entity (`CBTintBlockEntity`) stores an RGB colour per tint region.
- Every dyeable block implements `IColorableBlock` (creates the block entity, handles dyeing with leather-armour mixing). Override `getTintRegionCount` / `getTintRegion` / `getRegionForTintIndex` / `getAddedRegion` for multi-region blocks (see `CBTintableSlab`).
- Colouring is free (no dye consumed). There is no washing. Broken blocks always drop at the default colour (plain `dropSelf`, no `copy_components`).
- Shapes done: full block, stairs, two-tone slab, vertical slab, wall, button, pressure plate, vertical column, horizontal column, accented pillar (wall/floor/ceiling), accented pillar cap, connected window.
- Custom Blockbench models with body (tintindex 0) + accent (tintindex 1): extend `CBAccentedBlock`, list the model's element boxes (north-facing) as `CBPixelBox`es, and return the blockstate x/y quarter turns per state. Shapes, click-to-dye-region and datagen rotations all come from those. Hand-made parent models live in `models/block/` and use `texture_one` / `texture_two` (`CBModelTemplates.TEXTURE_ONE/TWO`).
- Window (`CBTintableWindow`, datagen in `CBWindowModels`, not part of the family): facing north/east only; joins to same-facing windows up/down/left/right (left/right = the model's north/south edges). Six hand-made `window_tintable_singlepane_*` models, rotated in-plane with blockstate x rotations, cover all 16 join combinations; `CBWindowModels.choose` picks model + rotation automatically. Corner properties (`up_left` etc.) add generated 2x2 corner frame pieces where both edges are joined but the diagonal window is missing. Blockstate is multipart (window part + corner parts). Frame = region 0 (`tintable_stone`), glass = region 1; the first dye on the glass sets `tinted_glass=true`, swapping `cb_glass` for `tintable_glass` (a reset tool is planned).
- Block sets: each texture is a `CBBlockSet` (record of all 12 shapes) registered with one `CBBlockRegistry.registerSet(name, displayName, CBMaterial)` line and listed in `CBBlockRegistry.SETS`. The set name = base block id = texture file name. `CBMaterial` (STONE/WOOD/METAL) holds map colour, sound, button/plate set type, tool tag and tags.
- Everything loops over `SETS` or the block register: models + windows (`CBBasicModelProvider`), tags, loot (`dropSelf`, slab table for `SlabBlock`), lang (`CBLanguageProvider`, no hand-written en_us.json), creative tab, shape recipes (`shapeRecipes`), client tints (one source per tint region of every `IColorableBlock`), block entity type.
- Adding a texture: PNG + one `registerSet` line + add to `SETS` (+ optional base block recipe). Adding a new shape: block class, a field in `CBBlockSet` (+ `blocks()`), register it in `registerSet`, a `CBTintedBlockFamily` method and a lang suffix in `CBLanguageProvider`.- Datagen: models via `CBTintedBlockFamily` (hand-written `tinted_*` parent models, or `ExtendedModelTemplateBuilder` for generated ones). Recipes and loot tables go through `GatherDataRegistryEntriesEvent`. Each model file must be created only once per datagen run (create shared models before loops).
- Window bends: a window with exactly one in-line window on an east/west side and one on a north/south side becomes an L (`bend` property: none/north_west/north_east/south_east/south_west). Bend models are generated in `CBWindowModels.bendTemplate` for north_west and rotated; for bends, left/right = first/second arm.
- Beams can have a `modelXTurns()` base rotation (chain models are made running north-south) and `turnCount()` 1/2/4 (`turn` property). `connectionPoint(...)` lets another kind of beam snap to a spot when placed against it.
- Chained support beam: renders the plain `bolted_support_beam` plus a generated half-chain (`chain_beam_half.json`, tintindex 1) on each side whose `chain_<side>` flag is on (sides = as the beam stands after its turn). The half-chain follows the beam across its side but never along its own length, so it always starts at the block edge. Chains (vanilla `ChainBlock` or `CHAIN` kind beams) attach only when lined up within half a pixel.
- Colour sources: `CBDataMaps.BLOCK_COLORS` data map (hex colour per block, `DataMaps/CBBlockColor`, datagen `CBBlockColorProvider`). Colour Picker (`CBColorPickerItem`) reads a block's colour; `CUSTOM_DYE` carries `DYED_COLOR` and dyes like a vanilla dye (`IColorableBlock.dyeColorOf`). `CBPickedDyeRecipe` crafts picker + dye into a custom dye (picker is returned). Tinting multiplies the texture, so dark textures give darker results.
- Bolted beams (`CBBoltedBeamBlock`): `Kind` (SQUARE, I_BEAM, CHAIN, CHAIN_MEDIUM, CHAIN_LARGE) decides what lines up; `offset_x/offset_z` place the body in whole pixels; caps have a 6-way `facing`, beams an `axis`; `alwaysUpright()` blocks have neither (facing is always UP). `bestFit` (protected) picks offsets/turn to match a target box. Datagen (`CBBoltedModels`) makes one model copy per position/turn moved by a NeoForge root transform. All bolted/chain/sconce/lantern blocks are listed in `CBBlockRegistry.BOLTED` (creative tab, tags).
- Chains: `CBChainSize` (SMALL, MEDIUM modelled centred at y 10, LARGE) holds footprint, plate and offset properties; `CBChainBeam` / `CBChainBeamCap` take a size via an anonymous subclass overriding `size()`. Chained support beams accept SMALL or MEDIUM (`chainSize()`).
- Torch sconce (`CBSconce`): horizontal `facing`, `torches` 1-3 (right-click with a sconce adds, shears remove and drop one), `lit` (light 15, flame particles), waterloggable; water or wind charge puts it out, torch / flint and steel relights. Drops one sconce per torch (`getDrops`). Models `sconce_torch_single/double/tripple`, textures `sconce_torch` / `sconce_torch_off`.
- Chain lanterns (`CBChainLantern`, an `alwaysUpright` chain-kind beam): small/medium via `size()`, cap versions via `hasPlate()`. Chain lanterns hang under a matching chain beam/cap, a chained support beam's lower side, or a vanilla chain (small), lined up and copying the chain's metal colour; with no chain they stand on the floor (`hanging=false`, models `chain_lantern` / `chain_medium_lantern`) and switch back when a chain is placed above. Caps hang under full-face blocks. Unsupported lanterns fall (`FallingBlockEntity.fall(...).disableDrop()`) and on landing shatter, lighting a fire if lit (`Fallable.onBrokenAfterFall`). `lit` stays on in water; wind charge or shears put it out, torch / flint and steel relights. Glass works like windows (`tinted_glass`). Region 0 metal, region 1 glass; `texture_three` (fasteners, untinted) is metal for now.
- Model conventions: tinted faces need `"tintindex"` (0 = metal/body, 1 = glass/accent); texture keys reference slots with `#` (`"1": "#texture_two"`). Chain-style models are made running north-south with the top at the north end (`modelXTurns() = 3`).
- Tech blocks (`CBTintableTechBlock`, `CBTintableTech3DBlock`): full metal blocks, region 0 stone base, region 1 glowing lines (`tintable_pulsing`). Glow elements use element-level `"light_emission": 15` + `"neoforge_data": { "ambient_occlusion": false }`. Flat version: base faces inset 0.01 under the glow faces (coplanar opaque faces z-fight); click region comes from a 16x16 pattern mapped per face. Raised version: lines stand 1px out of a stone core; a click in the outer layer on exactly one axis is a line.
- Storage: `ITintHolder` is what dyeing/picker/tint sources read; `CBTintData` holds colours for block entities that extend vanilla containers. `IColorableBlock#usesTintBlockEntity()` false for those, `getDefaultColor(region)` for non-white defaults.
- Chest (`CBTintableChest`, extends vanilla `ChestBlock`): bottom is a block model, lid drawn by `CBTintableChestRenderer` from standalone models (`*_lid_textured`). Diamond/gold on the knob locks it to the placer (diamond: no automation, owner-only breaking; both explosion-proof). Barrel (`CBTintableBarrel`): opens for players or redstone.
- Bulk storage (`Blocks/Storage`): `CBBulkItemHandler` (NeoForge transfer API, one item type per slot, any amount), `CBBulkStorageBlock` (+ block entity, shared `bulk_storage` type). New piles = subclass with shape/tint regions, capacity + item tag in the constructor (`CBIngotPile` c:ingots, `CBLogPile` minecraft:logs).
- Recipes: set blocks only come from the stonecutter, 1:1 within each set's item tag (`CBTags.SET_TAGS`, extras listed per set). Keep stonecutter counts at 1 to avoid dupes. Only stone and log have a recipe for their first block.

## 26.x notes
- Render layer (solid/cutout/translucent) is chosen per face from the texture's alpha; models no longer set a render type. Use `noOcclusion()` on see-through blocks.
- Multipart blockstates: `MultiPartGenerator.multiPart(block).with(BlockModelGenerators.condition().term(...).term(...), variant)`; chained terms are ANDed.
- `PropertyDispatch.initial(...)` works with up to 5 properties; `BlockModelGenerators.X_ROT_*`, `Y_ROT_*`, `UV_LOCK`, `ROTATION_HORIZONTAL_FACING` are available.
- Textures in datagen are `Material`s (`net.minecraft.client.resources.model.sprite.Material`): `new Material(identifier)`, `TextureMapping.put(slot, material)`.
- `useItemOn` returns `InteractionResult.SUCCESS` / `PASS` / `TRY_WITH_EMPTY_HAND`; damage a tool with `stack.hurtAndBreak(1, player, hand)` (use the `hand` parameter, not `getUsedItemHand()`).
- `updateShape(state, LevelReader, ScheduledTickAccess, pos, direction, neighborPos, neighborState, random)`; schedule ticks through `ScheduledTickAccess`. Block entity save/load uses `ValueOutput` / `ValueInput`.
- Wind charges: `onExplosionHit` with `explosion.canTriggerBlocks()`.
- Loot: `BlockLootSubProvider(Set.of(), FeatureFlags.REGISTRY.allFlags(), context)`; `NumberProvider` is now `ContextIntProvider` (`ContextIntProviders.exactly(n)`).
- Data maps: `DataMapType.builder(...).synced(...)`, registered in `RegisterDataMapTypesEvent`, read with `block.builtInRegistryHolder().getData(TYPE)`.
- Recipe serializers are a `MapCodec` + `StreamCodec`; `CustomRecipe` has a no-arg constructor; NeoForge `getCraftingRemainder(ItemInstance)` returns an `ItemStackTemplate`.

## MowLib (shared library)
- This mod depends on MowLib (mod id `mowlib`, package `com.mowmaster.mowlib`), bundled with Jar-in-Jar from
  mavenLocal (`com.mowmaster.mowlib:mowlib`, range `[0.0.1,1.0.0)`). Source: `Mowmaster/MowLib`, branch
  `NeoForge-26x`; the version this project builds against is the tag matching `prefer` in build.gradle.
- Before writing a shared system (tinting, storage, filters, transport, paging, knapping, bonus drops, tooltips,
  renderers...), clone MowLib and check whether it already exists there. Use it; don't copy it into this mod.
- Don't edit MowLib from this project's session. If something belongs in MowLib, or MowLib needs a change, write
  it up as a `mowlib-from-<mod id>.zip` (MowLib files + notes + migration), the same way as before.
- MowLib's CLAUDE.md lists what it contains and its rules.
